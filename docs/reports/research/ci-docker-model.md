# CI, Docker targets и защита веток

Контекст: [Wayfinder #11](https://github.com/guility/agents-template/issues/11). Это исследование, без изменения CI-правил. Проверен `agents-template` на `f4b9a55fc45f9b7ce2f5705f7bea6579053bd647` и состояние GitHub protection на 2026-11-20.

## Что есть сейчас

- GitHub Actions запускает основной workflow только на `push` в `main`; SAST/complexity идут параллельно, языковые тесты ждут их, а сводка запускается с `always()`. [ci-cd.yml](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/.github/workflows/ci-cd.yml#L3-L46)
- Корневой GitLab CI также разрешает только `push` в default branch. В подключённой конфигурации уже задан порядок `sast → build → security → tests → push → fetch_secrets → deploy`. [root CI](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/.gitlab-ci.yml#L1-L7) · [stages](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/.gitlab/ci/.gitlab-ci.yml#L8-L21)
- GitLab build сохраняет tar-архивы образов; scanner читает эти архивы. Но сборщик ищет только Dockerfile верхнего уровня `deploy/Dockerfiles/`, не выбирает `production`/`tests` target, а `required-tests` запускает Python-скрипты на runner и запускает все четыре suites в одной команде. [build job](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/.gitlab/ci/images.yml#L1-L40) · [build script](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/scripts/ci/images/build-images.sh#L4-L26) · [test job](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/.gitlab/ci/tests.yml#L1-L13) · [test runner](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/scripts/ci/run-required-tests.sh#L11-L26)
- В `deploy/Dockerfiles/` и `deploy/Dockerfiles/tests/` пока только placeholders, значит target-образов для проверки ещё нет. [production dir](https://github.com/guility/agents-template/tree/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/deploy/Dockerfiles) · [tests dir](https://github.com/guility/agents-template/tree/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/deploy/Dockerfiles/tests)
- Live GitHub GET branch-protection для `main` вернул `404 Resource not found` в `guility/agents-template` и `guility/agents-template-langs` (2026-11-20); этот endpoint возвращает 404, когда protection resource не найден. [GitHub API: Get branch protection](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection). Настройки GitLab в репозитории не хранятся, поэтому их текущее состояние этим исследованием не подтверждено. [GitLab protected branches](https://docs.gitlab.com/user/project/repository/branches/protected/)

## Практическая схема

### Targets и передача образа

- В Dockerfile задавать именованные stages `production` и `tests`; `tests` строить как `FROM production AS tests` и добавлять только тестовые библиотеки. Docker поддерживает сборку отдельного именованного stage через `--target`. Это оставляет runtime target компактным, а unit harness — потомком production stage. [Docker multi-stage builds](https://docs.docker.com/build/building/multi-stage/)
- Это два разных финальных образа: `tests` получает дополнительные слои и не должен называться тем же digest, что `production`. Для требования «security и unit проверяют тот же образ» нужно сканировать и запускать unit именно на одном `tests` image ID; production target сканировать отдельно. Docker image ID — SHA-256 идентификатор конфигурации и слоёв, а registry manifest digest — отдельный digest манифеста. [Docker image IDs](https://docs.docker.com/reference/cli/docker/image/pull/) · [registry digest](https://docs.docker.com/learn/content/prove-where-your-image-came-from/)
- После SAST и complexity один раз собрать оба target; `docker save`-нуть `tests` и сохранить ID/commit в manifest артефакта. Security и unit jobs загружают тот же archive (`docker load`) и сверяют ID перед работой. Docker save/load сохраняет образы и tags; GitHub artifacts передают данные между jobs, GitLab artifacts доступны через `needs:artifacts`. [Docker save](https://docs.docker.com/reference/cli/docker/image/save/) · [Docker load](https://docs.docker.com/reference/cli/docker/image/load/) · [GitHub artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data) · [GitLab artifacts](https://docs.gitlab.com/ci/yaml/#needsartifacts)
- Для обеих платформ базовый граф: `sast (Semgrep + gitleaks) + complexity → build production/tests → scan production/tests → unit на tests image`. На защищённом main после merge добавить `integration → mutation → e2e`; publish registry/deploy только после требуемых checks. Это проектное предложение, согласованное с текущими SAST jobs, complexity workflow и Docker targets. [SAST jobs](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/.gitlab/ci/sast.yml) · [complexity workflow](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/.github/workflows/complexity-check.yml#L6-L17) · [GitLab stages](https://github.com/guility/agents-template/blob/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/.gitlab/ci/.gitlab-ci.yml#L8-L21) · [Docker targets](https://docs.docker.com/build/building/multi-stage/)

### События, credentials, runners

- GitHub: `pull_request` к `main` (opened, synchronize, reopened) выполняет ранние проверки; `push` только в `main` проверяет то, что попало в protected branch, и добавляет оставшиеся suites. Не включать push для feature branches и `pull_request.closed`: так pre-merge и post-merge пути разделяются фильтрами событий. `pull_request` fork workflow получает read-only `GITHUB_TOKEN` и без repository secrets; не использовать `pull_request_target`, когда проверяется/исполняется код PR. [workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) · [fork security](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)
- GitLab: `workflow:rules` сначала допускает `merge_request_event`, затем `push` в default branch; push в branch с `$CI_OPEN_MERGE_REQUESTS` запрещает, затем при необходимости допускает push в branch без MR. Иные источники завершаются `when: never`. GitLab описывает такое переключение, чтобы push в открытую MR не создавал одновременно branch- и MR-pipeline. [workflow rules](https://docs.gitlab.com/ci/yaml/workflow/) · [duplicate pipelines](https://docs.gitlab.com/ci/jobs/job_rules/#avoid-duplicate-pipelines)
- Не передавать production registry/deploy secrets в PR/MR build и тесты. GitHub ограничивает fork `pull_request`; в GitLab protected variables/runners зависят от protected refs, а доступ protected variables к MR может быть включён отдельно. Для untrusted GitLab MR использовать изолированный rootless BuildKit builder без privileged mode и credentials; сохранить текущий protected DIND runner для доверенного main/push этапа. Rootless BuildKit не требует privileged containers, но self-managed runner должен разрешать нужные syscalls. [GitHub fork policy](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) · [GitLab variables](https://docs.gitlab.com/ci/variables/) · [protected runners](https://docs.gitlab.com/ci/pipelines/#pipeline-security-on-protected-branches) · [rootless BuildKit](https://docs.gitlab.com/ci/docker/using_buildkit/)

### Защита main и локальный hook

- GitHub: для `main` включить required pull request, required status checks для уникальных имён ранних CI jobs, запретить force-push/deletion и bypass администраторами; ограничить прямой push. GitHub branch protection поддерживает PR/status requirements, push restrictions и настройку запрета обхода. [protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- GitLab: для `main` задать `Allowed to merge` только разрешённым reviewers/maintainers, `Allowed to push and merge: No one`, approvals/status checks по политике проекта, force-push выключить. В документации GitLab именно `No one` в push/merge setting блокирует прямой push. [protected branches](https://docs.gitlab.com/user/project/repository/branches/protected/)
- Добавить локальный `pre-push` hook, который отказывает для remote ref `refs/heads/main`, но считать его только подсказкой: Git позволяет пропустить hook через `git push --no-verify`; запрет должен обеспечивать серверный branch protection. [Git pre-push hook](https://git-scm.com/docs/githooks#_pre_push) · [bypass flag](https://git-scm.com/docs/git-push#Documentation/git-push.txt---no-verify)

### Summary и README

- GitHub job summary поддерживает Markdown через `$GITHUB_STEP_SUMMARY`; отдельный финальный job создавать только при `success()`, `github.ref == 'refs/heads/main'`, push event и `github.ref_protected == true`. README-матрицу обновлять в этом же trusted job, дать `contents: write` только ему. [job summary](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#adding-a-job-summary) · [protected ref context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context)
- GitLab: собирать JUnit/Markdown-матрицу в отдельном финальном publish job только при успешных зависимостях, `push` в default branch и `$CI_COMMIT_REF_PROTECTED == "true"`; там же прикрепить JUnit через `artifacts:reports:junit` и Markdown как artifact. Нельзя публиковать JUnit report на ранних jobs при строгом success-only требовании: GitLab загружает `artifacts:reports` даже при неуспехе. [JUnit reports](https://docs.gitlab.com/ci/testing/unit_test_reports/) · [artifact behavior](https://docs.gitlab.com/ci/yaml/#artifactsreports) · [protected ref variable](https://docs.gitlab.com/ci/variables/predefined_variables/)
- Автокоммит README не должен запускать повторный CI: GitHub push через `GITHUB_TOKEN` и GitLab push через разрешённый `CI_JOB_TOKEN` не запускают новый pipeline; у GitLab push job token требует включить project setting. Ограничить write-доступ только publish job. [GitHub token events](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow) · [GitLab job token push](https://docs.gitlab.com/ci/jobs/ci_job_token/#allow-git-push-requests-to-your-project-repository)

## Ограничения

- До добавления Dockerfile нельзя проверить фактические OS/package managers, размер test-stage, команды запуска suites или точные check names; проект сейчас содержит только placeholders. [Dockerfile dirs](https://github.com/guility/agents-template/tree/f4b9a55fc45f9b7ce2f5705f7bea6579053bd647/deploy/Dockerfiles)
- Если «один digest» означает registry manifest digest, его до push в registry нет; до push следует закреплять передачу по одному build archive и Docker image ID, а после push записать возвращённый registry digest. Image ID и manifest digest имеют разное назначение. [Docker IDs](https://docs.docker.com/reference/cli/docker/image/pull/) · [manifest digest](https://docs.docker.com/learn/content/prove-where-your-image-came-from/)
- Текущее состояние GitLab protection зависит от настроек проекта и в YAML не читается; проверить его нужно отдельно в GitLab project settings/API. [GitLab protected branches](https://docs.gitlab.com/user/project/repository/branches/protected/)
